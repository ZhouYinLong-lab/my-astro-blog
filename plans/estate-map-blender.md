# 寒柳别苑 Blender 地图规划

## 目标

把现有 `/world` 页面从静态 2.5D PNG 地图升级为一座可探索的低多边形 3D 数字庭院：访客可以理解站点结构、点击区域进入对应页面，同时保留现有地图作为低性能设备和加载失败时的回退方案。

## 当前基础

- `src/pages/world/index.astro` 已经提供了全屏地图页面、主题切换、返回首页和区域点击入口。
- `public/world/estate-dark.png` 与 `estate-light.png` 是当前地图视觉基准，尺寸和构图应作为 Blender 第一版的参考。
- `/garden` 与 `/chores/garden` 已经承载语义地图，不应把文章 embedding、UMAP 节点或语义距离直接塞进 Blender 场景。
- 项目已经有 `/portfolio`、`/labs`、`/republic` 等可作为地标或作品入口的现成资源。

## 产品定位

Blender 地图不是一个游戏，也不是完整的 3D 博物馆，而是一个有空间隐喻的站点导航页。

核心体验：

1. 进入页面后，访客先看到完整的别苑布局。
2. 悬停或点击建筑时，显示名称、简介和入口提示。
3. 点击建筑进入现有站点页面，不改变正文阅读路径。
4. 首屏 2 秒内能看懂主要区域，不要求用户学习操作方式。

## 空间结构

第一版只做五个主要区域和少量地标，避免建模范围失控。

| 区域 | 空间形态 | 站点入口 | 内容含义 |
| --- | --- | --- | --- |
| 寒柳别苑主庭院 | 中央庭院、主屋、门楼 | `/` | 网站首页与作者总入口 |
| 机杼工坊 | 木工坊、工具墙、工作台 | `/chores/making/` | 项目、工具、工程决策 |
| 尺蠖实验室 | 小型实验室、数据屏、棋盘或网格 | `/blog/` 或技术分类 | Agent、算法、概率与系统实验 |
| 留丝书斋 | 书房、书架、案台 | `/blog/` 或人文分类 | 读书、影评、诗歌和写作 |
| 语义花园 | 花圃、节点树、雾化小径 | `/chores/garden/` | 文章之间的语义关系 |

辅助地标：会客间、友链码头、更新日志牌、项目展示台。第一版只放 2—4 个，不能让辅助地标抢过五个主区域。

## 视觉方向

采用“低多边形数字庭院 + 东方园林构图 + 轻微赛博材质”的方向：

- 等距或近似等距摄像机，固定主视角；
- 平面化色块、少量倒角、低复杂度树木和建筑；
- 主色沿用现有世界地图的纸张绿、深墨绿、暖金色；
- 白天模式明亮、纸质、偏园林；
- 夜间模式深绿、暖窗光、少量发光标记；
- 不使用过度写实材质、复杂粒子、实时阴影堆叠或大面积透明玻璃；
- 标签和说明文字由网页 HTML 负责，不把大量中文文字烘焙到 3D 贴图里。

## Blender 资产分层

### 场景层

- `Scene_Main`: 主场景、摄像机、灯光、世界背景。
- `Scene_Light`: 浅色主题渲染配置。
- `Scene_Dark`: 深色主题渲染配置。
- `Collection_Navigation`: 可点击区域对应的对象集合。
- `Collection_Decor`: 不参与交互的树、石头、灯、围墙和水面。

### 建模层

- 地面：一张带轻微高差的平面或分块地形。
- 建筑：模块化墙体、屋顶、门窗、牌匾框架。
- 植物：3—5 种低模树和灌木，实例化重复使用。
- 道路：主路、支路和通往区域的视觉动线。
- 地标：每个主区域一个足够独特的轮廓，不依赖文字才能区分。

### 材质层

- `MAT_Ground_Light` / `MAT_Ground_Dark`
- `MAT_Wood`
- `MAT_Roof`
- `MAT_Stone`
- `MAT_Water`
- `MAT_Glow_Dark`
- `MAT_Accent_Gold`

材质数量控制在 10—15 个以内，优先使用颜色和轮廓建立识别度。

## 交互技术方案

### 推荐方案：Blender 负责资产，网页负责交互

1. 在 Blender 中建模并导出 `.glb`。
2. 用 Three.js 或现有轻量 WebGL 组件加载模型。
3. 通过对象名称识别可点击区域，例如 `nav_home`、`nav_making`、`nav_garden`。
4. 网页侧完成射线检测、悬停高亮、点击跳转、无障碍文本和主题切换。
5. 用 CSS/HTML 叠加中文标题、简介和键盘焦点状态。

不建议把交互逻辑固化在 Blender 导出的动画或纹理中，因为后续修改网址、标题和导航文案会变得困难。

### 兼容与回退

- 桌面端支持 WebGL 时加载 3D 地图。
- 移动端或低性能设备优先提供静态 PNG 地图。
- `prefers-reduced-motion: reduce` 时关闭相机入场和物体浮动动画。
- WebGL、模型加载或网络失败时显示现有 `estate-light.png` / `estate-dark.png`。
- 所有入口必须同时存在于 HTML 链接中，不能只依赖 Canvas 点击。

## 资源与性能目标

- 第一版 `.glb` 目标：压缩后不超过 3 MB，理想值 1—2 MB。
- 首屏地图纹理尽量不超过 1 MB；优先使用纯色材质和 SVG/小尺寸纹理。
- 桌面端目标：中等设备稳定 50—60 FPS。
- 移动端不强制加载完整 3D 模型。
- 不把文章图片、视频和音频直接嵌入地图模型。

## 开发阶段

### Phase 0：空间草图

- 从现有 `estate-light.png` 和 `estate-dark.png` 提取布局关系。
- 确定主视角、画布比例、五个主区域位置和道路走向。
- 用 Blender 基础几何体完成灰盒，不制作细节。
- 产出一张浅色和一张深色静帧。

验收：不看标签也能大致区分中心庭院、工坊、实验室、书斋和花园。

### Phase 1：低模资产

- 建立可复用的建筑、树、围墙、道路和地标组件。
- 完成昼夜两套材质与灯光。
- 统一比例、轮廓和色彩。
- 用脚本或集合命名保证可导出对象稳定。

验收：模型可以作为静态主视觉使用，渲染图与现有网站风格统一。

### Phase 2：静态网页接入

- 导出压缩 `.glb`。
- 新建地图渲染组件，先只支持旋转/缩放或固定相机中的一种。
- 接入 `/world`，保留 PNG fallback。
- 把已有 `rooms` 配置改造成统一的导航数据源。

验收：五个主区域可以点击进入正确页面，主题切换正常，禁用 JavaScript 时仍能看到入口。

### Phase 3：交互和可访问性

- 增加悬停高亮、焦点高亮和区域说明卡片。
- 支持键盘访问和移动端触摸。
- 加入加载状态、错误状态和 reduced-motion 处理。
- 测试深色/浅色、桌面/手机、慢速网络和 WebGL 不可用环境。

验收：地图不是唯一导航方式；读屏、键盘和低性能设备仍能访问所有核心页面。

### Phase 4：内容联动

- 为每个区域显示文章数量、最近更新或代表项目。
- 允许从地标卡片进入具体项目或文章。
- 如果后续需要，再增加“夜游模式”、季节变化或动态灯光。

验收：交互增强了内容发现，而不是只增加装饰和加载成本。

## 推荐的数据结构

```ts
type EstateRegion = {
  id: string;
  label: string;
  subtitle: string;
  description: string;
  href: string;
  objectName: string;
  fallbackPosition?: { left: string; top: string; width: string; height: string };
};
```

Blender 对象名、网页配置和 PNG fallback 的热区必须使用同一组 `id`，避免 3D 地图与现有静态地图产生两套导航逻辑。

## 暂不做的事情

- 不在第一版制作可自由行走的第一人称 3D 游戏。
- 不为每篇文章制作一个建筑或模型。
- 不把语义花园的节点关系复制进物理地图。
- 不做实时多人访问、存档和复杂角色动画。
- 不为了视觉效果引入大型 3D 引擎或高分辨率贴图。

## 主要风险

| 风险 | 处理方式 |
| --- | --- |
| 建模范围不断膨胀 | 第一版锁定五个区域和少量地标 |
| 3D 加载影响博客体验 | 小模型、延迟加载、PNG fallback |
| 地图好看但不知道怎么点 | HTML 导航、区域说明、清晰 hover/focus 状态 |
| Blender 导出对象名称不稳定 | 统一命名规则和导出检查清单 |
| 3D 地图与现有视觉冲突 | Phase 0 先做昼夜静帧，再进入接入 |
| 地图变成纯装饰 | 每个区域必须对应真实页面或内容入口 |

## 完成标准

第一版完成的标志不是“场景很复杂”，而是：

- 访客能在 5 秒内理解五个主要区域；
- 地图有明确的作者世界观，但不妨碍导航；
- 模型加载失败时站点仍可用；
- 3D 资源不会显著拖慢 `/world`；
- 后续新增项目只需更新导航数据，不必重新建模；
- 现有语义花园、博客列表和项目页仍保持各自职责。

- 本轮完成 Phase 0 和第一版低模研究：五个主区域、一个会客间、门楼、石井、池塘、拱桥与简化柳树。
- 生成脚本：`tools/build-estate.py`，Blender 4.5.3 LTS，固定随机种子，可重复生成。
- 可编辑场景：`artifacts/estate/estate-day.blend` 与 `estate-night.blend`。
- 网站资产：`public/world/blender/`，含昼夜 PNG、GLB、导航及相机投影数据。
- 当前模型：44 个网格、25,716 个三角面，GLB 为 1,686,212 字节，未使用 Draco 压缩。
- 评审页：`/world/blender/index.html`，提供昼夜和标签切换、六个区域链接；为静态渲染预览，不是实时 WebGL。
- 现有 `/world/` 暂未替换。Phase 2 和 Phase 3 仍待实施，不能把资源体积达标当作浏览器 FPS 验收通过。
- 第一轮视觉检查：全院在画面内，昼夜轮廓一致；池塘部分遮挡、工坊室内细节与柳树垂枝是下一轮精修重点。布局尚待用户评审。
- 导出对象按区域与材质合并，以便后续做射线选中；网页投影标签来自 Blender 相机计算。

## 第二版约束与调整

- 用户要求按原地图制作；房间可以开门或开窗，但不能整面没有墙。
- 因此所有房屋补齐正立面、山墙和天花，门窗按实际洞口建模；部分门扇固定半开，部分关闭。
- 左右厢房转向院心，相机改为正面偏少量侧角的俯视机位；瓦垄使用深色，取消第一版浅色条纹。
- 第一版上方统计是历史记录，新模型统计以 `public/world/blender/regions.json` 为准。
- 不把固定半开姿态视作门窗交互已实现；实时查看器仍属后续阶段。

## 2026-09-15 第三版：像素风方向

- 用户认可固定视角渲染与像素风方向，并要求持续精进。保留“所有房间有完整墙体”的约束。
- 已在 Blender 原生几何中加入层叠筒瓦、错缝铺地、木构立面、墙脚苔藓、垂柳叶簇、竹林与生活物件。原版产物不覆盖，新版前缀为 `estate-pixel`。
- 原生渲染尺寸 640×480，网页提供 2 倍细节放大与旧版对照。相机一致，沿用程序投影热点；无自由相机。
- 第一轮成图存在夜间采样噪点和稀疏柳叶，第二轮补密植被、收敛瓦片色差、提高采样并降噪。
- 新模型已通过 Blender 重新导入检查：6 个导航根节点及 href 保留，55,177 三角面，Draco GLB 420,660 字节。
- pixel-art 技能用于原生像素尺寸与放大规则，webapp-testing 用于昼夜、对照、地标、移动端与无 JS 导航检查。
- 本轮仍为程序渲染的像素风研究，尚未达到原图的手绘细节密度。门窗开关动画未完成。
- 新增依据 Blender 相机投影对齐的 7 处夜灯微光、2 处池塘水纹 CSS 动效，支持手动开关和 reduced-motion；对照旧版时不显示这些叠加。
- 预览已通过桌面/手机、昼夜、旧版对照、地标显隐、放大滚动、无 JS 导航检查；截图保存于 `artifacts/estate/pixel-preview-*.png`。
- 后续重点：在完整墙体前提下增加侧厢房可读的门窗，进一步细化石板破损与植物轮廓；局部动画需要从同一镜头输出对齐图层。
